# Naming and Editorial Guide

[Documentation](README.md) / Naming and Editorial Guide

## Project Name and Code Identifiers

| Context | Required form | Example |
|---|---|---|
| Project title, documentation heading, prose, software citation title | **RAP-WAM** | `# RAP-WAM` |
| Full paper title | Preserve the published title exactly | See [citation.bib](../citation.bib) |
| Python package, imports and Hydra targets | `rap_wam` | `rap_wam.policy.rap_policy.RAPPolicy` |
| Source directory, distribution name and artifact prefix | `rap_wam` | `rap_wam-0.2.3.zip` |
| Console commands and configuration identifiers | Preserve the actual identifier | `rap_wam_train`, `encoder_name: rap_wam` |
| Existing copyright and upstream notices | Preserve attribution and license wording | See [third-party notices](../THIRD_PARTY_NOTICES.md) |

Use the display name when discussing the method or project. Use code formatting for literal imports, paths, keys and commands. Do not turn an underscore-separated package name into a reader-facing project heading, and do not change executable identifiers to match typography.

## Titles and Navigation

Use one clear top-level heading per document. Use Title Case for section headings, preserve proper names such as RoboDojo, Wan2.2, PyTorch and UMT5, and keep API/field spelling exact. Present the README subtitle as descriptive text rather than jumping from the main heading to a lower heading level.

A contents entry should name and link to its own section. Update both the visible label and anchor when renaming a heading. Prefer descriptive link labels such as “Configuration Reference” over bare filenames in introductory prose.

## README Information Architecture

Place the method overview as the first content figure immediately after the title and navigation. Introduce the research contribution and attributed results before setup instructions. Keep installation, supported workflows and training entry points ahead of optional galleries.

Keep all task previews accessible in small, labeled, collapsible groups, with original-video links and the scored/supplementary boundary visible before expansion. Put prediction comparisons and diagnostic plots after the training entry points. Use the documentation index for detailed procedures rather than duplicating complete manuals on the homepage.

Check the default collapsed layout and the fully expanded layout on desktop and narrow screens. The method figure must precede every task montage or animation, all 16 task previews must remain present, and training links must be reachable before the gallery.

## Technical Language and Evidence

Define a method abbreviation when first used. Lead with the supported user workflow, then link to tensor schemas and implementation details. Keep commands copyable, clearly identify paths the reader must supply, and describe the actual CLI rather than an imagined convenience flag.

Separate reported paper results, release validation and user-run experiments. State material reproduction differences once in the appropriate section and link to the detailed protocol. Figure captions should identify the source and distinguish research illustrations from outputs generated by the public recipe.

## Review Checklist

- Display name and code namespace are used in their respective contexts.
- Document titles, navigation labels, captions and package/citation metadata agree.
- Existing copyright attribution and formal author names are preserved.
- English prose is concise, spelling is consistent and headings have a clear hierarchy.
- Local references, code-block syntax and citation consistency pass `python scripts/check_docs.py`.
- Desktop and narrow-screen previews load all images without horizontal page overflow.
